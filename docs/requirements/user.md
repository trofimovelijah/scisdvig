# Пользовательские сценарии
## U-REQ-01. Пользователь должен иметь возможность загружать документ через веб-интерфейс

Статус: `draft`

Формулировка:
> Пользователь должен иметь возможность загружать документ через веб-интерфейс.

Критерии приёмки:
- Загрузка доступна из веб-интерфейса без обращения к файловой системе сервера.
- Принимаются документы `pdf` (`F-REQ-02`) размером до `200 Mb` (`U-REQ-03`).
- После успешной загрузки документ отображается в интерфейсе и доступны действия по `F-REQ-00`.
- Загруженный оригинал сохраняется без изменений для последующей обработки по `F-REQ-13`.

Проверка:
- UI-тест загрузки валидного документа.
- Тест сохранности оригинала: контрольная сумма файла до и после загрузки совпадает.

Связанные материалы:
- `U-REQ-02`, `U-REQ-03` — отказы и лимит размера.
- `F-REQ-02` — формат.
- `F-REQ-13` — сохранение оригинала.

## U-REQ-02. При невозможности загрузить документ пользователю должна возвращаться удобочитаемая информация о причине отсутствия возможности загрузки

Статус: `draft`

Формулировка:
> При невозможности загрузить документ пользователю возвращается удобочитаемое сообщение с конкретной причиной отказа.

Критерии приёмки:
- Сообщение содержит конкретную причину из контролируемого перечня: превышение размера документа, неподдерживаемый формат, повреждённый файл.
- Текст сообщения на русском языке, без технических деталей реализации.
- Отказ не прерывает работу приложения; повторная загрузка доступна без перезапуска.

Проверка:
- Тесты отказа по каждой причине перечня с проверкой текста сообщения.
- Тест повторной загрузки после отказа.

Связанные материалы:
- `U-REQ-03` — лимит размера.
- `F-REQ-02` — поддерживаемый формат.
- `U-REQ-05` — сообщения об ошибках этапов.

Примечание:
К причинам невозможности загрузки документов относятся следующие:
  - превышение размера документа
  - не поддерживаемый формат документа

## U-REQ-03. Допустимый размер загружаемого документа ограничен `200 Mb`

Статус: `draft`

Формулировка:
> Допустимый размер загружаемого документа ограничен `200 Mb`. Лимит применяется до начала обработки.

Критерии приёмки:
- Документ размером до `200 Mb` включительно принимается.
- Документ свыше `200 Mb` отклоняется с сообщением по `U-REQ-02`; обработка не запускается.
- Значение лимита задано конфигурацией и задокументировано.

Проверка:
- Граничные тесты: документы чуть меньше, ровно и чуть больше `200 Mb`.

Связанные материалы:
- `U-REQ-01` — загрузка.
- `U-REQ-02` — сообщение об отказе.

## U-REQ-04. Пользователь должен видеть прогресс выполнения обработки документа

Статус: `draft`

Формулировка:
> Пользователь должен видеть прогресс выполнения обработки документа.

Критерии приёмки:
- В UI отображается текущий этап обработки по `F-REQ-06` и его смена по мере выполнения.
- Отображение прогресса доступно на всём протяжении обработки, включая длительные этапы.
- При ошибке этапа вместо прогресса отображается сообщение по `U-REQ-05`; при отмене — состояние отмены по `U-REQ-09`.

Проверка:
- UI-тест смены этапов на контрольном переводе.
- Тест отображения при инжектированной ошибке и при отмене.

Связанные материалы:
- `F-REQ-06` — отображение этапов workflow.
- `U-REQ-05`, `U-REQ-09` — ошибки и отмена.

## U-REQ-05. Пользователю возвращается сообщение при ошибке выполнения этапов перевода документа

Статус: `draft`

Формулировка:
> Пользователю возвращается сообщение при ошибке выполнения этапов перевода документа.
>
> Ошибка описывает конкретное поведение на конкретном этапе перевода. Язык ошибки — русский. Отладочная информация содержится в логе, а не в сообщении пользователю.

Критерии приёмки:
- Сообщение указывает этап, на котором произошла ошибка, и понятную пользователю причину.
- Отладочные сведения доступны в логе и связаны с заданием; в UI они не отображаются.
- После ошибки пользователю доступны допустимые действия: отмена по `U-REQ-09` либо повтор/продолжение, если этап это допускает.
- Ошибка одного этапа не теряет результаты уже завершённых этапов.

Проверка:
- Инжектирование ошибки на каждом этапе контрольного перевода с проверкой текста сообщения.
- Проверка связи сообщения с записью в логе по идентификатору задания.

Связанные материалы:
- `F-REQ-06` — отображение этапов.
- `U-REQ-04` — прогресс.
- `U-REQ-09` — отмена.
- `F-REQ-20` — отчёт обработки.

## U-REQ-06. Пользователь перед переводом выбирает из выпадающего списка предметную область/тематику перевода

Статус: `draft`

Формулировка:
> Пользователь перед переводом выбирает из выпадающего списка предметную область/тематику перевода.
>
> На момент запуска `MVP` достаточно одной тематики — технической.

Критерии приёмки:
- Список тематик формируется из `themes.yaml`; для `MVP` доступна техническая тематика.
- Выбор тематики инициирует фоновую загрузку модели (`TS-04`) и отображение её готовности (`TS-05`).
- Перед переводом выполняется этап классификации тематики текста для выбора оптимальной модели или подхода; результат классификации доступен в отчёте обработки.

Проверка:
- UI-тест выбора тематики и появления статуса готовности модели.
- Тест формирования списка из `themes.yaml` без изменения кода.

Связанные материалы:
- `TS-04`, `TS-05` — фоновая загрузка и готовность модели.
- `NF-REQ-06` — отображение переключения.
- `F-REQ-05` — ориентация на техническую документацию.

## U-REQ-07. Пользователь может запрашивать превью перевода

Статус: `draft`

Формулировка:
> Пользователь может запрашивать превью перевода — предварительный перевод выбранного фрагмента до запуска полного перевода.
>
> Функция опциональна; в рамках `MVP` не приоритетна.

Критерии приёмки:
- Превью выполняется для ограниченного фрагмента и явно помечено как предварительный результат.
- Запрос превью не блокирует и не подменяет основной перевод.
- Для превью допускается отдельная «лёгкая» модель из реестра по `F-REQ-12`.

Проверка:
- UI-тест запроса превью на контрольном фрагменте с отметкой о предварительности.

Связанные материалы:
- `F-REQ-12` — реестр моделей (модель предпросмотра).
- `U-REQ-04` — прогресс основного перевода.

## U-REQ-08. Пользователь видит расход токенов по этапам перевода
Статус: `draft`

Формулировка:
Как пользователь-переводчик, я хочу видеть количество входных и выходных токенов по каждому этапу, использующему LLM, чтобы оценивать расход токенов при переводе документа.

Критерии приёмки:
- После завершения этапа в интерфейсе отображается расход токенов по всем вызовам LLM на этом этапе, включая повторные попытки.
- Данные представлены в таблице с указанием этапа, модели, способа запуска, количества входных и выходных токенов и их суммы.
- Если на этапе использовались разные модели или способы запуска, для каждой комбинации отображается отдельная строка.
- Если счётчики недоступны хотя бы для одного вызова, расход помечается как неполный; отсутствующие значения не заменяются нулями.
- Отображается общий расход токенов за текущий запуск перевода с указанием неполноты данных, если она есть.

Табличный вид:
| Этап | Используемая модель | Способ запуска | Входные токены | Выходные токены | Всего токенов | Полнота данных |
|------|---------------------|----------------|---------------:|----------------:|--------------:|---------------:|
|      |                     |                |                |                 |               |                |
| Итого |                    |                |                |                 |               |                |

Проверка:
1. Выполнить тестовый перевод с заранее известными счётчиками, несколькими этапами и повторным вызовом LLM.
2. Убедиться, что после завершения каждого этапа появляется соответствующая строка, а значения совпадают с суммой счётчиков его вызовов.
3. Проверить разделение строк при использовании разных моделей или способов запуска.
4. Проверить общий расход за запуск перевода.
5. Повторить проверку с вызовом без счётчиков: убедиться, что данные отмечены как неполные и отсутствующие значения не заменены нулями.

Связанные документы:
- [Учёт расхода токенов LLM](llm-usage-accounting.md)
  (REQ-TOKEN-01…08).

## U-REQ-09. Пользователь может отменить перевод документа в любой момент после его загрузки

Статус: `draft`

Формулировка:
> Пользователь может отменить перевод документа в любой момент после его загрузки.

Критерии приёмки:
- Действие отмены доступно на любом этапе обработки после загрузки, включая состояния ожидания решения (`F-REQ-08`, `F-REQ-19`).
- После отмены последующие этапы не запускаются и выполняющийся этап завершается по определённому правилу; повторный запуск требует нового задания.
- При отмене загруженные модели освобождаются по `F-REQ-11`; результат отмены отображается в UI и фиксируется в отчёте обработки.
- Действия пользователя после отмены не изменяют состояние завершённого задания.

Проверка:
- Интеграционный тест отмены на каждом контролируемом этапе с проверкой отсутствия дальнейших переходов.
- Тест освобождения ресурсов и повторного запуска как нового задания.

Связанные материалы:
- `F-REQ-08` (сценарий Е), `F-REQ-19` (сценарий Б) — отмена в состояниях ожидания.
- `F-REQ-11` — освобождение моделей.
- `F-REQ-20` — отчёт при отмене.
- `docs/adr/ADR-002-resume.md` — поведение после перезапуска (кандидат).

## U-REQ-10. Документы именуются по шаблону при скачивании (экспорте) 

Статус: `draft`

Формулировка:
> При скачивании (экспорте) документов они именуются по шаблону.
>
> Шаблон соответствует формуле: `yyyy-mm-dd`-`name`.`format`.
>
> Формирование `name` также нужно продумать дополнительно.

Критерии приёмки:
- Имя экспортированного файла соответствует шаблону `yyyy-mm-dd`-`name`.`format`.
- Дата в имени — дата экспорта; `format` соответствует выбранному формату по `F-REQ-14`.
- `name` формируется из имени исходного документа, нормализованного к нижнему регистру, без пробелов и спецсимволов; правило нормализации задокументировано.
- Совпадение имени при повторном экспорте разрешается суффиксом, без перезаписи существующего файла.

Проверка:
- Модульный тест генератора имени: нормализация, дата, формат, конфликт имён.
- Экспорт-тест с проверкой фактического имени файла в `depositary` по `NF-REQ-08`.

Связанные материалы:
- `NF-REQ-08` — локальное хранение переведённых документов.
- `F-REQ-14` — экспорт и форматы.
