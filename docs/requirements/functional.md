# Функциональные требования

## F-REQ-00. Приложение должно переводить загруженный документ на выбранный язык

Статус: `draft`

Формулировка:
> Приложение должно переводить загруженный документ на выбранный язык из доступного списка.
> 
> Основной язык для перевода - русский.
> 
> По-умолчанию в списке не выбран ни один язык.
>
> Для каждого фрагмента, выбранного для перевода, система сохраняет `fragment_id` и итог: перевод либо явную ошибку.

Сценарии использования:

  А. Выбор языка перевода
    1. Пользователь загрузил документ
    2. Из выпадающего списка выбран язык перевода
    3. Активна кнопка "**Начать перевод**"
    4. В ходе выполнения перевода отображается запись "_Идёт перевод на N-язык_"

  Б. Выбор языка оригинала документа
  1. Пользователь загрузил документ
  2. Выбран язык ориганала документа из выпадающего списка
  3. Активна кнопка "**Начать перевод**"
  4. Через некоторое время после начала перевода появляется запись "_Язык перевода соответствует языку оригинала. Перевод нерационален_"
  5. Доступен выпадающий список языков для перевода
  6. Кнопка "**Начать перевод**" неактивна

  В. Язык не выбран в выпадающем списке
  1. Пользователь загрузил документ
  2. В выпадающем списке не выбран язык для перевода
  3. Кнопка "**Начать перевод**" неактивна

Критерии приёмки:
- Каждый входной `fragment_id` присутствует в отчёте обработки.
- Для каждого `fragment_id` указан один итоговый статус.
- Потеря обязательного фрагмента исключает общий статус успеха.
- Сбой экспорта не уничтожает готовый результат перевода.
- Доступен выпадающий список языков для перевода
- В выпадающем списке не отображается по-умолчанию ни один язык
- В выпадающем списке присутствует русский язык на следующей позиции после позиции по-умолчанию
- После выбора языка становится активной кнопка "**Начать перевод**"
- После нажатия кнопки "**Начать перевод**" начинается процедура перевода

Проверка:
Интеграционный тест с успешным и ошибочным фрагментами;
отдельные проверки отсутствующего результата и ошибки экспорта.

## F-REQ-01. Приложение должно распознавать текстовый документ для дальнейшего перевода

Статус: `draft`

Формулировка:
> Приложение должно распознавать текстовый документ для дальнейшего перевода

Критерии приёмки:
- По загруженному документу определяются формат и тип содержимого: цифровой, сканированный или гибридный.
- Выбранный способ извлечения (текстовый слой, OCR, смешанный) соответствует определённому типу и фиксируется в отчёте.
- Документ неподдерживаемого формата отклоняется с сообщением по `U-REQ-02`, без запуска обработки.
- Невозможность определить тип содержимого фиксируется явно и не подменяется молчаливым выбором.

Проверка:
- Модульные тесты определения формата и типа содержимого на контрольном наборе (цифровой, скан, гибрид).
- Тест отклонения неподдерживаемого формата с корректным сообщением.

Связанные материалы:
- `F-REQ-02` — входной формат `pdf`.
- `F-REQ-13` — последующее извлечение содержимого и структуры выбранным способом.
- `U-REQ-02` — сообщения о невозможности загрузки.

Примечания:
  - Распознавание определяет пригодность документа и способ обработки; само извлечение содержимого выполняется по `F-REQ-13`.

## F-REQ-02. Перевод осуществляется для документов в формате `pdf`

Статус: `draft`

Формулировка:
> Перевод осуществляется для документов в формате `pdf`.

Критерии приёмки:
- Документ в формате `pdf` принимается и передаётся в обработку.
- Документ иного формата отклоняется с сообщением по `U-REQ-02` до начала обработки.
- Повреждённый или зашифрованный `pdf` приводит к явной ошибке загрузки, а не к молчаливому пустому результату.

Проверка:
- Тесты загрузки валидного `pdf`, файла иного формата, повреждённого и зашифрованного `pdf`.

Связанные материалы:
- `U-REQ-01` — загрузка через веб-интерфейс.
- `U-REQ-03` — ограничение размера.
- `F-REQ-13` — извлечение содержимого из `pdf`.

## F-REQ-03. Перевод осуществляется для документов в текстовом формате

Статус: `draft`

Формулировка:
> Перевод осуществляется для документов в текстовом формате.

Критерии приёмки:
- Документы `txt`, `md` и `ascii` принимаются и передаются в обработку.
- Правила защищённого содержимого по `F-REQ-15` и учёта по `F-REQ-20` применяются к текстовым форматам так же, как к `pdf`.

Проверка:
- Интеграционный тест перевода документа `md` с размеченными защищёнными элементами.

Связанные материалы:
- `F-REQ-02` — основной формат MVP.
- `F-REQ-15` — защищённое содержимое.

Примечания:
  - В рамках `MVP` не реализуется
  - К текстовым форматам относятся `txt`, `md`, `ascii`

## F-REQ-04. Перевод осуществляется с помощью LLM

Статус: `draft`

Формулировка:
> Перевод осуществляется с помощью LLM. Реализация переводчика основана на базе экосистемы LangChain/LangGraph

Критерии приёмки:
- Все вызовы моделей выполняются только через адаптер модели; UI и обработка документов не вызывают runtime инференса напрямую.
- Этапы обработки оркестрируются графом LangGraph; логика перевода и обработки документов находится вне графа.
- Workflow проходит контрольный сценарий с адаптером-заглушкой без реальной LLM.

Проверка:
- Интеграционный тест контрольного сценария с заглушкой модели.
- Статическая проверка/ревью: отсутствие прямых обращений к библиотеке инференса вне адаптера.

Связанные материалы:
- `NF-REQ-02` — LangGraph как средство оркестрации.
- `F-REQ-12` — модели локального инференса.
- `docs/adr/ADR-001-local-workflow.md` — границы компонентов.

## F-REQ-05. Приложение ориентировано на перевод технической документации на русский язык

Статус: `draft`

Формулировка:
> Приложение ориентировано на перевод технической документации на русский язык.

Критерии приёмки:
- Контрольный технический документ (стандарт/регламент) переводится EN→RU с применением принятого глоссария по `F-REQ-08`.
- Термины из принятого глоссария в переводе соответствуют зафиксированным переводам.
- Перевод на языки, отличные от русского, не входит в приёмку `MVP`.

Проверка:
- Интеграционный тест на контрольном техническом документе с эталонным глоссарием.
- Сопоставление переводов терминов с принятой версией глоссария.

Связанные материалы:
- `F-REQ-00` — выбор языка перевода.
- `F-REQ-07`, `F-REQ-08` — глоссарий и его принятие.
- `U-REQ-06` — выбор тематики перевода.

Примечания:
  - Предположительно в большинстве случаев язык оригинала документа - английский.
  - Перевод на другие языки допускается. К таковым относятся: немецкий, белорусский.
  - Отладка перевода на другие языки, кроме русского, в рамках `MVP` не реализуется.

## F-REQ-06. Каждый этап выполнения перевода должен отображаться в UI

Статус: `draft`

Формулировка:
> Каждый этап выполнения перевода должен отображаться в UI.
>
> Пользователь напрямую не пользуется `LangGraph`, однако должен представлять, что перевод осуществляется и на каком шаге находится. Статус выполнения перевода на каждом из этапов отображается в UE.
>
> Статус соответствует `State` в LangGraph, но с пояснением на русском языке. 

Критерии приёмки:
- Каждому состоянию workflow соответствует русскоязычное пояснение, отображаемое в UI; соответствие имён состояний — по `NF-REQ-07`.
- При переходе workflow отображение этапа обновляется без перезагрузки страницы.
- Ошибка этапа отображается в UI по `U-REQ-05`, а не только в логе.
- Состояния ожидания решения пользователя (`F-REQ-08`, `F-REQ-19`) отображаются как отдельные этапы.

Проверка:
- UI-тест смены отображаемых этапов на контрольном переводе.
- Тест отображения ошибки этапа и состояний ожидания решения.

Связанные материалы:
- `U-REQ-04` — прогресс обработки для пользователя.
- `U-REQ-05` — сообщения об ошибках этапов.
- `NF-REQ-02`, `NF-REQ-07` — workflow и именование состояний.

## F-REQ-07. Перед выполнением перевода должен формироваться глоссарий документа

Статус: `draft`

Формулировка:
> Перед переводом система должна сформировать глоссарий документа в рамках отдельного этапа workflow LangGraph.
>
> Глоссарий содержит выбранные термины, требующие единообразного или неоднозначного перевода, предлагаемые переводы, доступные определения и контекст употребления.
>
> Глоссарий не является полным перечнем терминов документа.
>
> Глоссарий должен храниться в JSON, быть связан с документом и иметь идентификатор версии.
>
> Запись глоссария должна содержать термин, перевод, область применимости, происхождение, даты создания и изменения, статус, а также определение и ссылку на источник при их наличии.
>
> Определения, сформированные системой, должны отличаться по метаданным от определений, извлечённых из документа.
>
> Для одной пары «термин + область применимости» допускается одна запись; запись для раздела имеет приоритет над записью для всего документа.
>
> UI должен отображать выполнение этапа, его успешное завершение или ошибку.
>
> Сформированный глоссарий передаётся на принятие по `F-REQ-08`; при отсутствии терминов передаётся пустой глоссарий.
>
> При ошибке формирования или сохранения глоссария перевод не запускается.

Критерии приёмки:

- До перехода к переводу workflow выполняет этап формирования глоссария и передаёт результат на принятие по `F-REQ-08`.
- Результат сохранён в JSON, соответствует спецификации глоссария и содержит идентификаторы документа и версии.
- На контрольном документе в глоссарии присутствуют все заранее размеченные обязательные термины; ссылки на источники соответствуют документу.
- Проверка отклоняет дубликаты пары «термин + область применимости», а выбор перевода учитывает приоритет записи раздела.
- UI отображает фактическое состояние этапа; при ошибке перевод не запускается.
- Отсутствие выявленных терминов приводит к формированию допустимого пустого глоссария, а не к ошибке.

Проверка:

- Модульные тесты структуры JSON, обязательных полей, дубликатов и приоритета записей.
- Интеграционный тест формирования глоссария на документе с эталонной разметкой.
- Тесты workflow для успешного выполнения, пустого результата, ошибок формирования и сохранения.
- UI-тест отображения состояний этапа.

Связанные материалы:

- `F-REQ-08` — проверка, редактирование и принятие глоссария.
- Спецификация глоссария — требуется описать JSON-схему, статусы, происхождение сведений и правила сопоставления терминов.
- Схема workflow LangGraph — требуется добавить ссылку на соответствующий документ.
- Контрольные документы с эталонной разметкой терминов — требуется подготовить.

Примечания:

  - Глоссарий является детерминированным хранилищем соответствий, а не векторным хранилищем.
  - Способ извлечения терминов, модель и runtime этим требованием не определяются.
  - Применение принятого глоссария и проверка соблюдения терминологии должны быть описаны в требовании к переводу.

## F-REQ-08. Пользователь должен иметь возможность проверить, изменить и принять сформированный глоссарий

Статус: `draft`

Формулировка:
> После формирования глоссария workflow LangGraph должен перейти в состояние ожидания решения пользователя.
>
> Пользователь может принять глоссарий, перейти к редактированию или отменить перевод.
>
> Если в течение 300 секунд с момента начала ожидания пользователь не выбрал действие, система автоматически принимает текущую версию и продолжает перевод.
>
> UI должен показывать глоссарий, доступные действия, предупреждение об автоматическом продолжении и оставшееся время; отсчёт определяется состоянием workflow, а не таймером страницы.
>
> Переход к редактированию отключает автоматическое продолжение.
>
> Пользователь может добавлять и удалять записи, изменять термины, переводы, определения и области применимости; система должна сохранять происхождение сведений и отмечать пользовательские изменения.
>
> Сохраняемая редакция должна соответствовать спецификации глоссария, не содержать пустых терминов и переводов, недопустимых областей применимости и дубликатов.
>
> В режиме редактирования запуск перевода доступен только после успешного сохранения текущей редакции; последующее изменение снова блокирует запуск.
>
> Сохранение само по себе не запускает перевод.
>
> Перед переводом система должна зафиксировать принятую версию, перевести её записи в статус `approved` и сохранить время и основание принятия: `user` или `timeout`.
>
> Перевод должен использовать зафиксированную версию глоссария.
>
> Отмена до начала перевода исключает его последующий запуск; ошибка сохранения или принятия блокирует запуск и отображается в UI.
>
> Конкурирующие и повторные события не должны приводить к нескольким переходам из одного состояния или повторному запуску перевода.

Сценарии использования:

  А. Глоссарий принят без изменений.
  1. Глоссарий сформирован, workflow ожидает решения пользователя.
  2. Пользователь нажимает «**Принять глоссарий**».
  3. Система фиксирует текущую версию с основанием `user`.
  4. Начинается перевод с использованием принятой версии.

  Б. Глоссарий принят автоматически.
  1. Выполнен шаг 1 сценария А.
  2. В течение `300` секунд пользователь не выбирает действие.
  3. Система фиксирует текущую версию с основанием `timeout`.
  4. Начинается перевод, UI отображает автоматическое продолжение.

  В. Глоссарий изменён и принят.
  1. Выполнен шаг 1 сценария А.
  2. Пользователь нажимает «**Редактировать глоссарий**», автоматическое продолжение отключается.
  3. Пользователь изменяет записи; кнопка «**Запустить перевод**» неактивна.
  4. Пользователь нажимает «**Сохранить изменения**».
  5. Система проверяет и сохраняет редакцию; кнопка «**Запустить перевод**» становится активной.
  6. Пользователь нажимает «**Запустить перевод**».
  7. Система фиксирует сохранённую версию с основанием `user` и начинает перевод.

  Г. Изменения не сохранены.
  1. Выполнены шаги 1–4 сценария В.
  2. Проверка записей или сохранение завершается ошибкой.
  3. UI отображает причину ошибки; кнопка «**Запустить перевод**» остаётся неактивной.
  4. Пользователь исправляет записи или повторяет сохранение при ошибке хранения.
  5. При успешном сохранении сценарий В продолжается с шага 6.

  Д. Глоссарий повторно изменён после сохранения.
  1. Выполнены шаги 1–5 сценария В.
  2. Пользователь изменяет запись.
  3. Кнопка «**Запустить перевод**» становится неактивной.
  4. Сценарий В продолжается с шага 4.

  Е. Перевод отменён.
  1. Workflow находится в состоянии ожидания решения или редактирования глоссария.
  2. Пользователь нажимает кнопку «**Отменить перевод**».
  3. Workflow переходит в состояние отмены; автоматическое продолжение отключается.
  4. UI отображает отмену; перевод не запускается.

Критерии приёмки:

- Сценарии `А–В` приводят к одному запуску перевода с соответствующей принятой версией и основанием принятия.
- Автоматический переход не выполняется до истечения `300` секунд и инициируется при достижении срока, если workflow продолжает ожидать решения.
- После входа в редактирование истечение первоначального тайм-аута не запускает перевод.
- Добавление, изменение и удаление записей доступны; недопустимая редакция не сохраняется.
- В сценариях `Г` и `Д` запуск заблокирован до успешного сохранения текущей редакции; сохранение не запускает перевод.
- При отмене или ошибке фиксации принятой версии перевод не запускается; UI отображает результат или ошибку.
- При конкурирующих и повторных событиях успешно выполняется не более одного перехода из текущего состояния.
- Правила принятия и редактирования одинаково применяются к пустому и непустому глоссарию.

Проверка:

- Модульные тесты валидации записей, фиксации версии и доступности запуска.
- Тесты workflow с управляемым временем для тайм-аута, редактирования и отмены.
- Интеграционные тесты сценариев `А–Е`, ошибок фиксации версии, конкурирующих и повторных событий.

- Каждый исключённый элемент имеет запись с идентификатором источника, причиной и применённым правилом.
- Для повторяющегося навигационного текста, исключённого как дубликат, указано сохраняемое представление соответствующих сведений.
- Пояснения и сноски в нижней области страницы сохраняются.
- При невозможности отделить служебную часть от содержательной весь блок сохраняется.
- Неопределённые блоки не исключаются автоматически и отражаются в отчёте обработки.
- Необъяснённая потеря блока или связи блокирует переход к формированию глоссария.

- Тесты блоков смешанного и неопределённого назначения.
- Интеграционный тест на размеченном документе с колонтитулами, сносками и пояснениями в нижней области страницы.
- Сравнение сохранённого представления до очистки и результата очистки с учётом зарегистрированных исключений.

## F-REQ-13. Приложение должно извлекать и сохранять содержимое и структуру PDF до очистки и перевода

Статус: `draft`

>
> Извлечение должно обеспечивать получение содержимого для проверки по `F-REQ-18` и структурированного представления для последующей обработки.
>
> Сохранённое представление должно включать извлечённые текстовые блоки, ресурсы, сведения об их происхождении, порядок чтения и выявленные связи.
>
> Для каждого элемента назначается идентификатор; сохраняются идентификатор документа, тип источника, исходное содержимое или ссылка на ресурс, страница и координаты, если они определены.
>
> Необходимо различать основной текст, заголовки, служебные колонтитулы, сноски, пояснения, примечания, предупреждения, ссылки и защищённое содержимое по `F-REQ-15`.
>
> Должны сохраняться выявленные связи между маркером сноски и её текстом, ссылкой и её целью, а также между ресурсом и местом его включения в документ.
>
> Невозможность определить тип блока, порядок чтения или цель связи должна фиксироваться явно. Неопределённость не разрешает удалять соответствующее содержимое.
>
> Текст аннотаций, полей форм, скрытых слоёв и метаданных сохраняется с указанием типа источника для проверки по `F-REQ-18`. Извлечение для проверки не означает обязательного включения этих сведений в перевод.
>
> Ошибки и выявленная неполнота извлечения отражаются в отчёте. Неполное извлечение обязательного содержимого не должно получать статус полного успеха.

Критерии приёмки:
- До очистки сохранены исходный PDF и представление извлечённого содержимого.
- Каждый извлечённый элемент имеет уникальный в пределах документа идентификатор и сведения о происхождении.
- На контрольном наборе извлечены все заранее размеченные обязательные блоки и ресурсы.
- Для всех заранее размеченных обязательных сносок и ссылок сохранены соответствующие связи.
- Блоки в верхней и нижней областях страниц не отбрасываются при извлечении.
- Для неопределённых типов и неразрешённых связей сохранены исходное содержимое и диагностическая запись.
- Ошибка OCR, чтения страницы или извлечения обязательного источника не подменяется пустым успешным результатом.
- Цифровые, сканированные и гибридные документы проверяются отдельными тестовыми примерами.

Проверка:
- Интеграционные тесты извлечения на версионируемом наборе PDF с эталонной разметкой.
- Проверка идентификаторов, происхождения, порядка чтения и связей.
- Тесты сносок, переходящих между страницами, повторяющихся маркеров и ссылок на разные типы объектов.
- Тесты ошибок OCR, недоступных страниц, неопределённого порядка чтения и неразрешённых связей.
- Отдельное сопоставление извлечённого содержимого с размеченным оригиналом для выявления потерь на этапе извлечения.

Связанные материалы:
- `F-REQ-10` — недеструктивная очистка.
- `F-REQ-15` — защищённое содержимое.
- `F-REQ-16` — обработка изображений.
- `F-REQ-18` — охват проверки признаков prompt injection.
- `F-REQ-20` — сквозной учёт содержания.

## F-REQ-14. Приложение должно экспортировать результат с сохранением содержания и связей

Статус: `draft`

Формулировка:
> Приложение должно предоставлять экспорт результата в `PDF`, `Markdown` и `LaTeX`. Формат по умолчанию — `PDF`.
>
> Экспорт выполняется по явному действию пользователя после завершения обработки и проверки результата.
>
> Экспортируемый документ должен включать переводимые блоки, сохранённое без перевода содержимое и ресурсы, предусмотренные результатом обработки.
>
> Тексты сносок, пояснений, примечаний и предупреждений должны включаться в результат вместе со связями с соответствующими местами документа.
>
> Допускается изменение расположения сносок и примечаний, включая перенос в конец раздела или документа, если сохранены их идентифицируемость, порядок и связи с маркерами.
>
> Адреса внешних ссылок должны сохраняться. Внутренние ссылки должны указывать на соответствующие объекты результата, а не на утратившие актуальность страницы оригинала.
>
> Если внутреннюю ссылку невозможно восстановить, её исходное обозначение сохраняется, а проблема явно отмечается в документе и отчёте. Такая ссылка не считается успешно восстановленной.
>
> При экспорте выполняется проверка полноты содержания и связей по `F-REQ-20`. Файл с обнаруженными необъяснёнными потерями не должен выдаваться как успешно проверенный результат.
>
> Ошибка экспорта не должна уничтожать результат обработки или препятствовать повторной попытке и выбору другого формата.
>
> При наличии ошибок обработки допускается отдельное действие экспорта неполного результата. Перед экспортом пользователь должен видеть предупреждение, а файл должен содержать отметку о неполноте и перечень известных проблем.

Критерии приёмки:
- Контрольный результат экспортируется во все три формата: `PDF`, `Markdown` и `LaTeX`.
- Каждый обязательный элемент результата присутствует в экспортированном документе либо имеет явную отметку об ошибке при экспорте неполного результата.
- Сноски и примечания однозначно сопоставляются с их маркерами.
- Внешние адреса совпадают с адресами в подготовленном результате.
- Восстановленные внутренние ссылки ведут к требуемым объектам.
- Неразрешённые ссылки не подменяются ссылками на неверные объекты.
- Защищённые элементы восстановлены без изменения их значений; допускается только экранирование, необходимое для формата экспорта.
- Неполный результат нельзя экспортировать под видом полного.
- После ошибки экспорта доступна повторная попытка без повторного перевода.

Проверка:
- Интеграционные тесты экспорта каждого формата.
- Сопоставление экспортированного документа с реестром элементов и связей.
- Тесты переноса сносок, внутренних ссылок, внешних адресов и защищённых элементов.
- Проверка открытия `PDF` и сборки экспортированного `LaTeX`.
- Тесты ошибки экспорта, повторной попытки и экспорта неполного результата.
- Визуальная проверка контрольных документов по чек-листу отображения структуры и примечаний.

Связанные материалы:
- `F-REQ-00` — результаты обработки переводимых фрагментов.
- `F-REQ-10` — исключённые служебные элементы.
- `F-REQ-13` — структура и исходные связи.
- `F-REQ-15` — восстановление защищённого содержимого.
- `F-REQ-16` — возвращение изображений в документ.
- `F-REQ-20` — проверка полноты.

Примечания:
  - Точное воспроизведение исходной пагинации, шрифтов и расположения элементов этим требованием не устанавливается.
  - Отчёт проверки должен различать полноту содержания и корректность отображения: наличие блока в файле само по себе не подтверждает его видимость и читаемость.


## F-REQ-15. Приложение должно разделять переводимый текст и защищённое содержимое

Статус: `draft`

Формулировка:
> До формирования глоссария и перевода приложение должно выделять содержимое, подлежащее переводу, и содержимое, которое необходимо сохранить без перевода.
>
> Защищённые элементы должны иметь идентификаторы и признак запрета перевода, например внутреннюю метку `no_translate`, независимо от используемой библиотеки обработки документов.
>
> При передаче текста модели защищённые элементы могут заменяться плейсхолдерами. Система должна сохранять соответствие между плейсхолдером и исходным элементом и восстанавливать элементы при сборке результата.
>
> Поясняющий текст сносок, примечаний, предупреждений, советов и других содержательных блоков должен переводиться независимо от расположения блока.
>
> Внутри переводимых блоков адреса, технические идентификаторы, код и другие защищённые элементы сохраняются без перевода.
>
> Маркеры сносок и идентификаторы целей ссылок не переводятся; их соответствия должны сохраняться при переводе и сборке.
>
> В ссылке переводится человекочитаемая подпись, если она не является защищённым идентификатором; адрес или идентификатор цели сохраняется либо преобразуется при экспорте с сохранением цели.
>
> Моноширинное оформление само по себе не является основанием для запрета перевода.
>
> В рамках MVP таблицы, формулы и диаграммы сохраняются без перевода как защищённые объекты. Внешние по отношению к этим объектам подписи и пояснения переводятся.
>
> Отсутствие, дублирование, изменение защищённого элемента или нарушение его связи должно выявляться проверкой по `F-REQ-20`.

Содержимое, сохраняемое без перевода:
- Inline-код, блоки кода, CLI-команды и вывод терминала.
- JSON/XML/YAML-сниппеты, регулярные выражения, BNF/EBNF.
- Имена переменных, функций, классов и другие программные идентификаторы.
- API-эндпоинты, URL, URI, пути к файлам и директориям.
- Плейсхолдеры, синтаксические теги и атрибуты.
- Числовые значения, специальные числовые записи и обозначения единиц измерения в составе защищённых выражений.
- Маркеры сносок и технические идентификаторы ссылок.
- Таблицы, формулы и диаграммы в пределах ограничений MVP.

Критерии приёмки:
- На контрольном наборе переведён весь размеченный обязательный поясняющий текст сносок, примечаний и предупреждений.
- Все размеченные защищённые элементы восстановлены без изменения значений.
- Для каждого плейсхолдера существует ровно одно ожидаемое восстановление в соответствующем месте результата.
- Повторяющиеся значения защищённых элементов не приводят к смешению их местоположения и связей.
- Ссылки, содержащие переводимую подпись и защищённый адрес, обработаны раздельно.
- Защищённые элементы проверяются после перевода, постобработки и сборки.
- Нарушение восстановления исключает статус полного успеха.
- Таблицы, формулы и диаграммы не теряются при сохранении без перевода.

Проверка:
- Модульные тесты выделения, замены и восстановления защищённых элементов.
- Тесты одинаковых значений в разных местах документа.
- Интеграционные тесты сносок и предупреждений с кодом, URL и техническими идентификаторами.
- Тесты намеренного удаления, изменения и дублирования плейсхолдеров моделью.
- Проверка сохранности защищённых объектов после постобработки и экспорта.

Связанные материалы:
- `F-REQ-10` — сохранение содержательных блоков при очистке.
- `F-REQ-13` — извлечение блоков и связей.
- `F-REQ-14` — экспорт и преобразование ссылок.
- `F-REQ-16` — изображения.
- `F-REQ-20` — учёт элементов и контроль потерь.

Примечания:
- `no_translate` обозначает внутреннюю семантику защиты, а не обязательное наличие одноимённого тега в `Docling`.
- В рамках MVP содержимое блоков кода, включая комментарии внутри кода, сохраняется без перевода.
- Перевод содержимого таблиц и диаграмм потребует отдельного расширения требований.


## F-REQ-16. Приложение должно извлекать изображения "как есть" и возвращать их в переведённый документ

Статус: `draft`

Формулировка:
> Приложение должно извлекать изображения "**как есть**" и возвращать их в переведённый документ по завершению основного перевода текста.
>
> Изображения не должны отдельно распознаваться для последующего перевода, а их содержимое не должно переводиться.
> 
> Порядок извлечения изображений из оригинального документа представлен в `Схеме работы с изображениями`

Схема работы с изображениями:
  - парсинг
  - защита от перевода - пометка тегом `no_translate`
  - хранение связи в `State` LangGraph
  - сборка в `md`/`LaTeX`/`pdf`

Критерии приёмки:
- Каждое изображение контрольного документа извлечено как ресурс со связью с местом включения по `F-REQ-13`.
- Изображения помечены `no_translate` и не передаются в вызовы LLM ни на одном этапе.
- Все размеченные изображения присутствуют в экспортированном результате в соответствующих местах включения для всех форматов по `F-REQ-14`.
- Потеря или подмена изображения выявляется контролем по `F-REQ-20`.

Проверка:
- Интеграционный тест на PDF с размеченными изображениями: извлечение, хранение связи в `State`, сборка в `md`/`LaTeX`/`pdf`.
- Контроль отсутствия обращений содержимого изображений к модели по журналам вызовов адаптера.
- Тест намеренного удаления изображения — контроль по `F-REQ-20` фиксирует потерю.

Связанные материалы:
- `F-REQ-13` — извлечение ресурсов и связей.
- `F-REQ-14` — возвращение изображений при экспорте.
- `F-REQ-15` — разделение переводимого текста и защищённого содержимого.
- `F-REQ-20` — учёт ресурсов.

Примечания:
  - Содержимое изображений не должно распознаваться и переводиться в рамках `MVP`.
  - Изображение = ресурс + плейсхолдер
  - рендер вместо извлечения

## F-REQ-17. Приложение должно использовать отдельный глоссарий для перевода под выбранную тематику

Статус: `draft`

Формулировка:
> Приложение должно использовать отдельный глоссарий для перевода под выбранную тематику.
>
> Сам глоссарий должен вестись в контроле версий в текстовом формате (`markdown`, `ascii`).
>
> При переводе глоссарий должен подключаться как внешняя библиотека или массив текста.

Критерии приёмки:
- При выполнении перевода приложение обращается за терминологией к внешнему подключаемому глоссарию
- Если глоссарий недоступен, перевод продолжается, но отображается сообщение об отсутствии доступа к глоссарию.

Проверка:
- Модульный тест загрузки внешнего глоссария из файла в контроле версий.
- Тест деградации: при недоступном глоссарии перевод продолжается, сообщение отображается.

Связанные материалы:
- `F-REQ-07`, `F-REQ-08` — глоссарий документа; тематический глоссарий не подменяет его.
- `U-REQ-06` — выбор тематики перевода.

Примечание:
  - В рамках `MVP` не используется, преждевременно. Далее перспективно. Использовать такой глоссарий в качестве образца.
  - Хороший задел на будущее и как перспектива для потенциального развития или даже монетизации - подключаемый из внешнего источника (из контроля версий) глоссарий для конкретной тематики формирует общий подход к терминологии. Потенциально можно слинковать с ГОСТами и иными стандартами.

## F-REQ-18. Приложение должно локально проверять извлечённое содержимое на признаки `prompt injection` до очистки и перевода

Статус: `draft`

Формулировка:
> Приложение должно проверять извлечённое содержимое документа на признаки `prompt injection` до очистки по `F-REQ-10`, формирования глоссария, перевода и постобработки.
>
> До проверки допускаются сохранение оригинала, извлечение, необходимые `OCR`/`layout`-операции, назначение идентификаторов и сохранение исходного представления по `F-REQ-13`. Эти операции не должны применять правила исключения служебных элементов.
>
> Проверка должна охватывать основной текст, заголовки, колонтитулы, сноски, пояснения, примечания, предупреждения, скрытые текстовые слои, текст аннотаций, значения полей форм и текстовые метаданные PDF.
>
> Проверяются также элементы, которые впоследствии могут быть исключены из перевода или сохранены без перевода.
>
> Результат проверки должен различать три состояния: «Признаки не обнаружены», «Признаки обнаружены», «Проверка не завершена».
>
> При обнаружении признаков последующие этапы блокируются до решения пользователя по `F-REQ-19`.
>
> При ошибке или невозможности проверить часть обязательного содержимого устанавливается состояние «Проверка не завершена». Доступны повторная проверка и отмена; продолжение недоступно.
>
> Для подозрительных фрагментов сохраняются текст, идентификатор исходного элемента, тип источника и расположение, если оно определено.
>
> Проверка не должна удалять или исправлять содержимое. Подозрительность фрагмента и его необходимость в переводе учитываются независимо.
>
> Проверка выполняется локально, без внешних сервисов. LLM-анализ допускается только через локальный инференс.
>
> Содержимое документа обрабатывается как недоверенные данные и не должно исполняться как инструкции приложению или его инструментам.

Критерии приёмки:
- Проверка завершается до запуска очистки, формирования глоссария и перевода.
- До проверки не применяются правила исключения по `F-REQ-10`.
- Для каждого обязательного извлечённого текстового элемента зарегистрирован результат проверки либо явная ошибка.
- Срабатывание содержит ссылку на исходный элемент, а не только копию подозрительного текста.
- Обнаружение признаков блокирует последующие этапы до подтверждения по `F-REQ-19`.
- Неполная проверка не считается отсутствием признаков и не допускает продолжения.
- Проверка не изменяет исходное содержимое.
- На согласованном версионируемом тестовом наборе `recall ≥ 0,90` и `FPR ≤ 0,05` для каждого поддерживаемого языка.
- Проверка выполняется без исходящих обращений к внешним сервисам.

Проверка:
- Тесты с инъекциями и без них во всех обязательных типах источников.
- Тесты фрагментов, одновременно являющихся полезным содержанием и содержащих признаки инъекции.
- Интеграционный тест порядка этапов и блокировки workflow.
- Тесты ошибки, неполной проверки и повторного запуска.
- Проверка связи срабатываний с исходными идентификаторами.
- Расчёт recall/FPR на согласованном наборе.
- Запуск без внешнего доступа с контролем исходящих соединений.

Связанные материалы:
- `F-REQ-10` — очистка после проверки.
- `F-REQ-13` — предварительное извлечение без исключения содержимого.
- `F-REQ-19` — решение пользователя.
- `F-REQ-20` — учёт охвата проверки.
- `docs/architecture.md` — порядок этапов и варианты организации проверки.

Примечания:
- Отсутствие обнаруженных признаков не означает гарантированную безопасность.
- Проверка содержимого самостоятельных изображений и вложенных файлов не входит в обязательный охват MVP.
- Текст, полученный OCR сканированных страниц по `F-REQ-13`, входит в охват проверки.
- Наличие известных непроверяемых источников вне охвата MVP указывается в отчёте.
- Модели, правила и пороги срабатывания описываются в архитектурных решениях `docs/architecture.md`.

Открытые вопросы:
1. Поддерживаемые языки и состав приёмочного набора.
2. Допустимое время проверки и условия измерения.

## F-REQ-19. Приложение должно запрашивать решение пользователя при обнаружении признаков `prompt injection`

Статус: `draft`

Формулировка:
> При обнаружении признаков `prompt injection` приложение должно приостановить последующие этапы и показать предупреждение с подозрительными фрагментами.
>
> Пользователь может явно продолжить обработку либо отменить её.
>
> Срок ожидания решения в рамках MVP — `8 минут` с момента перехода задания в состояние «_Ожидается решение пользователя_».
>
> Отсутствие ответа не считается согласием. При истечении срока задание завершается со статусом «_Истекло время ожидания_».
>
> Подтверждение разрешает продолжить подготовку документа, начиная с уточнения структуры и недеструктивной очистки по `F-REQ-10`. Оно не разрешает исполнять инструкции из документа, отключать проверки или автоматически удалять подозрительные фрагменты.
>
> Предупреждение должно сообщать, что продолжение не устраняет обнаруженные признаки.
>
> Подозрительные фрагменты отображаются как текст без исполнения их содержимого. Для них доступны тип источника и расположение, если оно определено.
>
> Решение фиксируется вместе с идентификатором задания, версией документа, идентификатором результата проверки и временем.
>
> Для другого документа, изменённого проверяемого содержимого или нового результата проверки требуется новое подтверждение.
>
> После продолжения сохраняются отметка «_Обработка продолжена после предупреждения_» и связь решения с результатом обработки.
>
> При состоянии «_Проверка не завершена_» продолжение недоступно.

Сценарии использования:

А. Пользователь продолжает обработку.
1. Приложение показывает предупреждение, подозрительные фрагменты и оставшееся время.
2. До истечения срока пользователь нажимает кнопку «**Продолжить перевод**».
3. Приложение фиксирует решение.
4. Возобновляется подготовка документа; дальнейшее исключение элементов допускается только по `F-REQ-10`.
5. Подозрительные содержательные фрагменты сохраняются и обрабатываются по общим правилам.

Б. Пользователь отменяет обработку.
1. Пользователь нажимает кнопку «**Отменить перевод**».
2. Задание завершается со статусом «_Обработка отменена пользователем_».
3. Последующие этапы не запускаются.

В. Срок ожидания истёк.
1. В течение `8 минут` решение не принято.
2. Задание завершается со статусом «_Истекло время ожидания_».
3. Последующие этапы не запускаются.
4. Запоздалое подтверждение не возобновляет задание.
5. Результат доступен при следующем обращении к заданию.

Критерии приёмки:
- До явного подтверждения последующие этапы заблокированы на стороне приложения.
- UI показывает предупреждение, фрагменты, оставшееся время и действия продолжения и отмены.
- Срок контролируется сервером; просмотр фрагментов, обновление страницы и восстановление соединения его не продлевают.
- Закрытие предупреждения или вкладки не считается решением.
- При достижении срока подтверждение отклоняется.
- Конкурирующие подтверждение, отмена и истечение срока приводят ровно к одному допустимому переходу состояния.
- Повторное подтверждение не запускает дублирующую обработку.
- Подтверждение для другого документа или результата проверки отклоняется.
- После отмены и истечения срока продолжение старого задания невозможно; повторный запуск требует нового задания и проверки.
- Продолжение не удаляет подозрительные фрагменты и не снимает ограничения локальной обработки.
- Отметка о продолжении после предупреждения доступна в результате и отчёте обработки.

Проверка:
- UI-тесты предупреждения, фрагментов, таймера и доступных действий.
- Интеграционные тесты продолжения, отмены и истечения срока с управляемым временем.
- Тесты обновления страницы, закрытия вкладки и восстановления соединения.
- Тесты одновременных и повторных действий.
- Тесты замены документа и результата проверки.
- Тест безопасного отображения фрагментов с разметкой и командами.
- Проверка сохранности подозрительного содержательного фрагмента после продолжения.

Связанные материалы:
- `F-REQ-10` — недеструктивная очистка.
- `F-REQ-18` — проверка признаков prompt injection.
- `F-REQ-20` — учёт решений и содержания.
- `docs/architecture.md` — приостановка и возобновление обработки.

Примечания:
- Срок `8 минут` относится только к ожиданию решения, а не ко времени перевода.
- Завершение задания не означает удаления его истории или выключения приложения.
- Продолжение после предупреждения не является подтверждением безопасности документа.

Открытые вопросы:
1. Срок хранения истории решений после завершения обработки.

## F-REQ-20. Обеспечение учёта содержания оригинального документа от извлечения до результата

Статус: `draft`

Формулировка:
> Приложение должно обеспечивать учёт содержания оригинального PDF от извлечения до результата и экспорта, обнаруживая необъяснённые потери блоков, ресурсов и связей на всём пути обработки.
>
> Учёт должен опираться на сохранённый оригинал и реестр элементов, сформированный при извлечении по `F-REQ-13`.
>
> Реестр должен включать идентификаторы элементов, их происхождение, исходное содержимое или ссылки на ресурсы, связи и назначенный способ обработки.
>
> Для каждого элемента фиксируется одно из назначений: перевод, сохранение без перевода, исключение по `F-REQ-10` либо использование только для проверки и диагностики.
>
> Назначение «только для проверки и диагностики» не должно применяться для исключения содержательного блока, подлежащего включению в результат.
>
> Для каждого элемента, включаемого в результат, должна сохраняться связь с соответствующим переводом, неизменённым содержимым или явной ошибкой обработки.
>
> Разбиение и объединение блоков допускаются при сохранении соответствий между всеми исходными и результирующими элементами.
>
> Контроль учёта выполняется после извлечения, подготовки к переводу, перевода, постобработки, сборки результата и экспорта.
>
> Необъяснённой потерей считается отсутствие ожидаемого элемента или связи без допустимого зарегистрированного основания. Явная ошибка объясняет отсутствие результата, но не делает обработку успешной.
>
> Обнаруженная потеря должна содержать сведения об исходном элементе, ожидаемом результате и этапе, на котором впервые выявлено расхождение.
>
> Потеря обязательного элемента, неразрешённая обязательная связь или незавершённый обязательный контроль исключают общий статус полного успеха.
>
> Приложение должно предоставлять отчёт с количеством учтённых элементов, их назначениями, результатами обработки, исключениями, ошибками и известными ограничениями проверки.
>
> Результат перевода и состояние его экспорта учитываются раздельно: ошибка экспорта не уничтожает готовый перевод.

Критерии приёмки:
- Каждый извлечённый элемент присутствует в реестре и имеет назначение.
- Для каждого элемента, подлежащего включению в результат, зарегистрированы результат обработки и соответствие исходному элементу либо явная ошибка.
- Все исключения по `F-REQ-10` имеют проверяемое основание.
- При разделении или объединении блоков все исходные идентификаторы остаются прослеживаемыми.
- Контроль обнаруживает намеренное удаление обязательного блока, ресурса, маркера сноски, текста сноски или связи.
- Контроль обнаруживает нарушение восстановления защищённых элементов по `F-REQ-15`.
- Отсутствие записи о проверке обязательного элемента по `F-REQ-18` не считается успешной проверкой.
- Необъяснённая потеря при подготовке блокирует переход к формированию глоссария.
- Ошибка или потеря на последующих этапах исключает общий статус полного успеха; неполный экспорт допускается только по `F-REQ-14`.
- Отчёт доступен как при успешном завершении, так и при ошибке или отмене; ещё не выполненные этапы обозначены явно.
- На контрольном наборе извлечённое представление отдельно сопоставляется с эталонной разметкой оригинала.

Проверка:
- Модульные тесты реестра, назначений, соответствий и итоговых статусов.
- Тесты разбиения и объединения блоков.
- Интеграционные тесты с намеренным удалением элементов на каждом контролируемом этапе.
- Тесты потери и подмены ресурсов, ссылок и сносок.
- Тесты ошибок перевода, постобработки, сборки и экспорта.
- Проверка согласованности отчёта с фактическими артефактами обработки.
- Отдельная проверка извлечения на размеченных оригиналах для обнаружения элементов, не попавших в реестр.

Связанные материалы:
- `F-REQ-00` — учёт переводимых фрагментов и их результатов.
- `F-REQ-10` — допустимые исключения.
- `F-REQ-13` — оригинал, извлечённое представление и происхождение элементов.
- `F-REQ-14` — полнота экспорта и неполный результат.
- `F-REQ-15` — защищённые элементы.
- `F-REQ-16` — изображения и их включение в результат.
- `F-REQ-18` — охват проверки признаков prompt injection.
- `F-REQ-19` — фиксация решения пользователя.
- `U-REQ-11` — доступ пользователя к отчёту.
- `docs/architecture.md` — контрольные точки workflow.

Примечания:
- Учёт идентификаторов не подтверждает смысловую точность перевода: присутствующий блок может быть переведён неверно. Оценка точности перевода требует отдельных проверок.
- Реестр извлечённых элементов сам по себе не обнаруживает содержимое, которое не было извлечено. Для этого используются проверки полноты извлечения и сопоставление с размеченными оригиналами.
- Приложение не должно заявлять доказанную полноту произвольного PDF только на основании совпадения количества входных и выходных блоков.
- Обязательными считаются элементы и связи, подлежащие обработке согласно требованиям и согласованному охвату; обязательность не определяется успешностью их извлечения.
- Формат реестра, отчёта и правила передачи идентификаторов между этапами должны быть определены в спецификации внутреннего представления документа.

Открытые вопросы:
1. Сроки хранения оригинала, извлечённого представления и отчёта.
2. Состав автоматических проверок полноты извлечения для произвольных документов.

## F-REQ-21. Приложение должно позволять повторить сбойный этап без перезапуска всего перевода

Статус: `draft`

Формулировка:
> При сбое этапа результаты и артефакты завершённых этапов сохраняются. Пользователю доступна возможность повторного запуска "сбойного" этапа.
>
> Повтор продолжает обработку с точки сбоя и не приводит к повторному выполнению успешно завершённых этапов.
>
> Повтор выполняется по явному действию пользователя после сообщения об ошибке по `U-REQ-05`.
>
> Повтор использует зафиксированные входные артефакты этапа (в том числе принятую версию глоссария по `F-REQ-08`) и не требует повторного принятия уже принятых решений пользователя.
>
> Повторные вызовы LLM при повторе этапа включаются в учёт расхода токенов как повторные попытки по `U-REQ-08`.

Критерии приёмки:
- При сбое этапа артефакты и реестр завершённых этапов не теряются; состояние учёта по `F-REQ-20` остаётся согласованным.
- После ошибки на этапе, допускающем повтор, в UI доступно действие повтора; после успешного повтора обработка продолжается со следующего этапа.
- Успешный повтор не дублирует записи принятия решений и не сбрасывает состояния ожидания по `F-REQ-08` и `F-REQ-19`.
- Для этапов, не допускающих повтор (например, после истечения срока по `F-REQ-19`), действие повтора недоступно.
- Расход токенов повторных попыток отображается в соответствующем этапе и не приводит к подмене данных учёта.

Проверка:
- Интеграционный тест: инжектированный сбой на каждом контролируемом этапе, затем повтор; проверка отсутствия повторного выполнения завершённых этапов.
- Тест сохранения принятой версии глоссария и решений пользователя при повторе.
- Проверка корректности учёта токенов при повторных вызовах.

Связанные материалы:
- `U-REQ-05` — сообщение об ошибке и допустимые действия.
- `U-REQ-09` — отмена как альтернатива повтору.
- `F-REQ-08`, `F-REQ-19` — состояния ожидания решения.
- `F-REQ-20` — согласованность учёта при повторе.
- `docs/requirements/llm-usage-accounting.md` — учёт повторных попыток.

Примечания:
  - В рамках `MVP`.
  - Восстановление обработки после перезапуска приложения находится вне границ требования — см. `docs/adr/ADR-002-resume.md` (кандидат, итерация I2).

## F-REQ-22. Качество перевода должно оцениваться на контрольном наборе отдельно от полноты учёта

Статус: `draft`

Формулировка:
> Качество перевода оценивается отдельно от учёта содержания по `F-REQ-20`: на версионируемом контрольном наборе документов с эталонными переводами или разметкой.
>
> Оценка включает терминологическую точность по принятому глоссарию и проверку смысловых сегментов; применение автоматических метрик принимается отдельным решением.
>
> Порог приемлемого качества фиксируется; результат оценки документируется и связывается с версией конфигурации и модели.
>
> Оценка выполняется при смене модели, шаблона промпта (`TS-02`) или лимитов обработки (`TS-03`).

Критерии приёмки:
- Контрольный набор документов с эталонной разметкой версионируется в репозитории.
- Определены метрики и порог приемлемости; результаты оценки отделены от статуса учёта по `F-REQ-20`.
- Смена модели или промпта сопровождается прогоном оценки на контрольном наборе.
- Результат оценки сохраняется и связан с версией конфигурации и идентификатором модели.

Проверка:
- Прогон оценки на контрольном наборе с фиксацией результата и его связи с версией конфигурации.
- Проверка, что неуспешная оценка качества не подменяет и не отменяет статус учёта по `F-REQ-20` (и наоборот).

Связанные материалы:
- `F-REQ-20` — граница между учётом содержания и качеством перевода (примечание).
- `F-REQ-07`, `F-REQ-08` — терминологическая точность по глоссарию.
- `TS-02`, `TS-03` — изменения, требующие повторной оценки.
- `NF-REQ-09` — версия конфигурации в результате.
- `adr/ADR-003-models.md` — оценки как основание выбора моделей.

Примечания:
  - Вне рамок `MVP`.
  - Зависит от `NF-REQ-09`.

## F-REQ-23. Приложение должно ограничивать и учитывать применение OCR

Статус: `draft`

Формулировка:
> Для `MVP` задаются ограничения применения OCR: максимальная доля страниц, обрабатываемых OCR, и порог качества распознавания.
>
> Значения порогов задаются конфигурацией; начальные значения фиксируются архитектурным решением после первых локальных замеров.
>
> Доля OCR-страниц и выявленные ошибки распознавания фиксируются в отчёте обработки.
>
> При превышении порога доли OCR-страниц пользователю отображается предупреждение о возможном снижении качества; обработка продолжается.
>
> Страницы, не распознанные OCR, отражаются в отчёте как известное ограничение и не подменяются успешным результатом.

Критерии приёмки:
- Пороги доли OCR-страниц и качества заданы конфигурацией и задокументированы; изменение не требует правки кода.
- Для гибридного и сканированного документов доля OCR-страниц определяется и отражена в отчёте.
- Превышение порога доли вызывает видимое в UI предупреждение до запуска перевода либо при его начале.
- Ошибки OCR отдельных страниц видны в отчёте обработки; документ с такими страницами не получает статус полного успеха ("`F-REQ-13`").
- Методика оценки качества OCR на контрольном наборе описана и связана с этим требованием.

Проверка:
- Интеграционные тесты на сканированном и гибридном PDF: определение доли, предупреждение, записи в отчёте.
- Граничный тест порога доли OCR-страниц.
- Тест ошибки OCR отдельной страницы: отсутствие статуса полного успеха.

Связанные материалы:
- `F-REQ-13` — извлечение, открытые вопросы о допустимых ошибках OCR и методике измерения (закрываются настоящим требованием по части рамок и порогов).
- `F-REQ-18` — OCR-текст входит в охват проверки.
- `F-REQ-20`, `U-REQ-11` — отражение ограничений в отчёте.
- `U-REQ-04` — отображение предупреждения.

Примечания:
  - В рамках `MVP`.
  - Численные значения порогов необходимо определить по результатам замеров на целевом наборе, затем зафиксировать в архитектурном решении.
