# Технические истории

## TS-01. Глоссарий хранится в формате `JSON`(`JSONL`)

Статус: `draft`

Формулировка:
> Глоссарий хранится в формате `JSON` (`JSONL`) с жёсткой схемой — как локальное хранилище версий переводчика в рамках `MVP`.
>
> Глоссарий формируется один раз на документ. По окончании этапа формирования глоссария модель освобождает память под модель перевода.

Критерии приёмки:
- Файл глоссария валиден по зафиксированной JSON-схеме; невалидный файл отклоняется с ошибкой.
- На один документ формируется один глоссарий с идентификатором версии по `F-REQ-07`.
- После завершения этапа глоссария память, занятая моделью формирования, освобождена (`F-REQ-11`).

Проверка:
- Модульный тест валидации файла по схеме, включая отказ для невалидного файла.
- Интеграционный тест освобождения памяти после этапа глоссария.

Связанные материалы:
- `F-REQ-07` — формирование и структура глоссария.
- `F-REQ-11` — принцип `RoT`.
- Спецификация глоссария — требуется описать JSON-схему (см. `F-REQ-07`).

## TS-02. Когда используется модель `TranslateGemma`, то применяется строгий шаблон промпта

Статус: `draft`

Формулировка:
> При использовании модели `TranslateGemma` промпт формируется строго по шаблону «Translate this from {src} to {tgt}: ...».
>
> Отклонение от шаблона недопустимо: модель переходит в режим диалога, и качество перевода падает.

Критерии приёмки:
- Генератор промпта для `TranslateGemma` формирует строки строго по шаблону; шаблон версионируется вместе с кодом.
- Изменение шаблона сопровождается контрольным прогоном качества перевода.

Проверка:
- Модульный тест генератора промпта на соответствие шаблону.
- Контрольный прогон на эталонных фрагментах при изменении шаблона.

Связанные материалы:
- `F-REQ-12` — модели локального инференса.
- `TS-03` — ограничение размера чанка.

## TS-03. Когда выполняется чанкование текста из pdf, размер одного чанка не должен превышать 2000 символов

Статус: `draft`

Формулировка:
> При чанковании текста из `pdf` размер одного чанка не должен превышать 2000 символов; целевой диапазон — 500–1500 символов.
>
> Ограничение техническое для ряда моделей (`TranslateGemma`); для остальных моделей большой чанк ведёт к потере контекста.

Критерии приёмки:
- Ни один чанк не превышает 2000 символов; превышение считается ошибкой подготовки.
- Разбиение не разрывает предложения и защищённые элементы по `F-REQ-15`.
- Лимит и целевой диапазон задаются конфигурацией пары «модель + runtime», а не константой в коде.

Проверка:
- Модульный тест чанковщика: предельный размер, границы предложений, границы защищённых элементов.
- Расширить этап `verify` проверкой «количество предложений входа ≈ количеству предложений выхода» (отдельная ТИ).

Связанные материалы:
- `F-REQ-15` — защищённое содержимое.
- `F-REQ-20` — учёт фрагментов.

Примечания:
  - Шаблон запроса и бюджет контекста следует проверять для конкретной пары «модель + runtime»

## TS-04. Когда тематика выбрана в `dropdown`, модель должна подниматься в фоне

Статус: `draft`

Формулировка:
> При выборе тематики в `dropdown` соответствующая модель поднимается в фоне — параллельно с `ingest`, до нажатия кнопки начала перевода.

Критерии приёмки:
- Загрузка модели инициируется событием выбора тематики без ожидания команды перевода.
- К моменту нажатия «Начать перевод» модель либо готова (`TS-05`), либо пользователь видит статус переключения по `NF-REQ-06`.
- Фоновая загрузка не блокирует загрузку и обработку документа.

Проверка:
- Интеграционный тест с замером таймингов: выбор тематики → начало загрузки модели → готовность до/после команды перевода.

Связанные материалы:
- `U-REQ-06` — выбор тематики.
- `TS-05` — сигнал готовности модели.
- `NF-REQ-06` — отображение переключения.
- `F-REQ-11` — принцип `RoT`.

## TS-05. Когда пользователь выбрал тематику перевода, отображается надпись "модель готова"

Статус: `draft`

Формулировка:
> Когда пользователь выбрал тематику перевода и модель фактически загружена, отображается надпись «модель готова».
>
> UX-честность: пользователь видит, почему первые секунды ничего не происходит.

Критерии приёмки:
- Надпись «модель готова» отображается только после подтверждённой готовности модели, а не по факту выбора тематики.
- Выбор тематики меняет значение в `themes.yaml`; изменение кода при этом не требуется.
- Повторный выбор той же тематики не вызывает повторную загрузку модели — идемпотентность.

Проверка:
- UI-тест появления надписи после фактической готовности.
- Тест идемпотентности повторного выбора тематики.
- Проверка, что смена тематики — правка только конфигурационного файла.

Связанные материалы:
- `NF-REQ-06` — ожидание при переключении модели.
- `U-REQ-06` — выбор тематики.
- `TS-04` — фоновая загрузка модели.

## TS-06. События обработки должны записываться в структурированный лог с идентификатором задания

Статус: `draft`

Формулировка:
> Каждое задание получает идентификатор задания. События обработки записываются в структурированный машиночитаемый лог.
>
> Запись лога содержит время, идентификатор задания, этап (имя состояния по `NF-REQ-07`), уровень и тип события.
>
> Сообщение об ошибке в UI по `U-REQ-05` однозначно сопоставляется с записью лога по идентификатору задания.
>
> Вызовы LLM фиксируются с метаданными (модель, этап, способ запуска, usage) согласованно с учётом токенов.
>
> Полный текст документа в лог не записывается - допускаются идентификаторы элементов и отрывки ограниченной длины.

Критерии приёмки:
- Все записи одного задания содержат общий идентификатор задания и извлекаются по нему полностью.
- По идентификатору из сообщения об ошибке находится соответствующая запись лога с этапом и причиной.
- Уровень детализации лога меняется конфигурацией без правки кода.
- Формат записей зафиксирован и проверяем; записи вызовов LLM согласованы с данными по `U-REQ-08`.

Проверка:
- Модульный тест формата записей и обязательных полей.
- Интеграционный тест: инжектированная ошибка этапа → запись лога, сопоставимая с сообщением пользователю.
- Проверка извлечения полного журнала задания по его идентификатору.

Связанные материалы:
- `U-REQ-05` — связь пользовательских сообщений с логом.
- `NF-REQ-07` — именование состояний, используемое в записях.
- `docs/requirements/llm-usage-accounting.md` — совместимость метаданных вызовов LLM.
- `F-REQ-20` — отчёт обработки поверх журнала событий.

Примечания:
  - В рамках `MVP`.
