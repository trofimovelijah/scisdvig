# Ограничения и нефункциональные требования

## NF-REQ-01. Допускается возможность запуска моделей либо локально, либо по API

Статус: `draft`

Формулировка:
> Способ запуска модели (локальный runtime либо вызов по API) определяется конфигурацией и скрыт за адаптером модели.
>
> По умолчанию используется локальный запуск; вызов внешнего API допускается только по отдельному зафиксированному решению.

Критерии приёмки:
- Переключение способа запуска выполняется конфигурацией без изменения кода workflow, перевода и UI.
- Исключительно адаптер модели различает локальный runtime и API.
- В конфигурации `MVP` по умолчанию задан локальный способ запуска.

Проверка:
- Интеграционный тест workflow с двумя реализациями адаптера без изменения остального кода.
- Ревью конфигурации по умолчанию.

Связанные материалы:
- `F-REQ-12` — модели локального инференса.
- `docs/adr/ADR-001-local-workflow.md` — заменяемость runtime через адаптер.

## NF-REQ-02. Для оркестрации процесса перевода используется LangGraph

Статус: `draft`

Формулировка:
> Оркестрация этапов перевода, ожидание решений пользователя и переходы состояний реализуются средствами LangGraph.
>
> LangGraph отвечает за workflow; бизнес-логика перевода, обработки документов и экспорта находится в отдельных компонентах.

Критерии приёмки:
- Этапы и переходы описаны графом LangGraph; состояния именованы по `NF-REQ-07`.
- Состояния ожидания пользователя (`F-REQ-08`, `F-REQ-19`) реализованы штатными средствами приостановки workflow.
- Workflow проходит контрольный сценарий с адаптером-заглушкой.

Проверка:
- Интеграционный тест контрольного сценария включая приостановку и возобновление.
- Ревью: отсутствие логики перевода в узлах графа.

Связанные материалы:
- `F-REQ-06` — отображение состояний в UI.
- `docs/adr/ADR-001-local-workflow.md` — границы компонентов.

## NF-REQ-03. Для функционирования приложения должны использоваться только библиотеки и пакеты с открытыми исходными текстами

Статус: `draft`

Формулировка:
> Все библиотеки и пакеты, используемые приложением, должны распространяться с открытыми исходными текстами под лицензиями, допускающими использование в проекте.

Критерии приёмки:
- Дерево зависимостей содержит только пакеты с проверяемыми открытыми лицензиями; перечень зафиксирован в репозитории.
- Добавление зависимости с неподходящей или неопределённой лицензией блокирует сборку.
- Требование относится и к runtime инференса; к моделям применяется отдельно `NF-REQ-05`.

Проверка:
- Автоматизированная проверка лицензий зависимостей (например, `pip-licenses`) в CI.
- Ревью отчёта проверки при изменении зависимостей.

Связанные материалы:
- `NF-REQ-05` — лицензии моделей.

## NF-REQ-04. Запуск приложения должен осуществляться с одной рабочей станции

Статус: `draft`

Формулировка:
> Запуск приложения должен осуществляться с одной рабочей станции.
>
> В качестве рабочей станции для MVP используется MacBook M5 Pro (Silicon, 64 Gb RAM, 1Tb SSD)
>
> В качестве средств запуска приложения необходимо использовать инструменты контейнеризации (docker/docker-compose с учётом MacOS), способные оркестрировать в том числе LLM.
>
> Инструменты типа `k8s` использовать не требуется ввиду их повышенной сложности для подобного локального приложения.

Критерии приёмки:
- Приложение запускается одной командой `docker-compose` на рабочей станции MVP (MacBook M5 Pro, 64 Gb RAM) по `docs/runbook.md`.
- Для запуска не требуются внешние обязательные сервисы и оркестраторы.
- Суммарное потребление памяти при обработке контрольного документа не превышает ресурсов станции с учётом `F-REQ-11`.

Проверка:
- Чистый запуск по `docs/runbook.md` на целевой станции с последующим контрольным переводом.
- Замер пикового потребления памяти при переводе контрольного документа.

Примечания:
  - Границу «контейнер приложения → локальный runtime» нужно проверить отдельно.

Связанные материалы:
- `F-REQ-11` — выгрузка простаивающих моделей.
- `docs/runbook.md` — инструкция запуска.
- `docs/architecture.md` — нерешённый вопрос границы контейнеризации.

## NF-REQ-05. LLM, используемые локально, должны обладать подходящими лицензиями для работы без ограничений и с открытыми весами

Статус: `draft`

Формулировка:
> LLM, используемые локально, должны обладать подходящими лицензиями для работы без ограничений.
> 
> У LLM должны быть открыты веса для локального инференса.

Критерии приёмки:
- Для каждой модели из реестра `docs/architecture.md` зафиксирована лицензия и подтверждена допустимость локального инференса.
- Веса модели скачиваемы и запускаются локально на рабочей станции по `NF-REQ-04`.
- Модель без подтверждённой лицензии не подключается к приложению.

Проверка:
- Ревью реестра моделей: наличие лицензии и результатов локального запуска для каждой записи.
- Контрольный запуск каждой подключаемой модели локально.

Связанные материалы:
- `F-REQ-12` — реестр моделей и выбор через `ADR-003`.
- `NF-REQ-03` — лицензии библиотек.

## NF-REQ-06. Допустимо ожидание при переключении модели

Статус: `draft`

Формулировка:
> Допустимо ожидание при переключении модели: не миллисекунды, а секунды.
>
> С точки зрения пользователя функциональные кнопки не должны быть активными в момент переключения. При простое более двух секунд должна появляться надпись "_идёт переключение моделей_".
>
> После надпись меняется на "модель готова" (см. TS-05)

Критерии приёмки:
- Во время переключения модели функциональные кнопки неактивны.
- При ожидании более двух секунд отображается надпись «_идёт переключение моделей_», по готовности — «модель готова» (`TS-05`).
- Переключение не прерывает уже выполняющийся этап и не приводит к запуску перевода на незагруженной модели.

Проверка:
- UI-тест переключения модели с замером времени появления надписей.
- Интеграционный тест: запуск перевода блокируется до фактической готовности модели.

Связанные материалы:
- `TS-04`, `TS-05` — фоновая загрузка и сигнал готовности.
- `F-REQ-11` — принцип `RoT`.
- `docs/requirements/technical-stories.md`

## NF-REQ-07. Каждый `State` в LangGraph должен использовать согласно `PEP8` snake_case с упоминанием функционального назначения из требований

Статус: `draft`

Формулировка:
> Каждый `State` в LangGraph должен использовать согласно `PEP8` snake_case с упоминанием функционального назначения из требований

Критерии приёмки:
- Все состояния workflow названы в `snake_case` и содержат указание на функциональное назначение из требований.
- Соответствие состояния требованию зафиксировано в схеме workflow или сопроводительной таблице.
- Состояние без русскоязычного пояснения для UI отсутствует (`F-REQ-06`).

Проверка:
- Код-ревью по чек-листу именования при изменении графа.
- Сопоставление списка состояний со схемой workflow и отображаемыми пояснениями.

Связанные материалы:
- `NF-REQ-02` — LangGraph.
- `F-REQ-06` — отображение этапов в UI.

## NF-REQ-08. Переведённые документы хранятся локально на сервере запуска приложения

Статус: `draft`

Формулировка:
> Переведённые документы хранятся локально на сервере запуска приложения.
>
> Например, в директории `depositary` текущего репозитория.
>
> Документы должны храниться упорядоченно в директориях по выделенному признаку (например, каталог по датам)

Критерии приёмки:
- Переведённые документы сохраняются в директории `depositary` репозитория с вложенным каталогом по дате перевода.
- Структура каталогов создаётся автоматически при первом сохранении.
- Имя файла формируется по шаблону `U-REQ-10`; при совпадении имён конфликт разрешается явно, без перезаписи.

Проверка:
- Экспорт контрольного документа и проверка его расположения и имени.
- Тест повторного экспорта одноимённого документа.

Примечания:
  - Вне рамок MVP возможно использовать отдельные файловые S3-хранилища (minIO), либо облачные хранилища.

Связанные материалы:
- `U-REQ-10` - именование документов при скачивании (экспорте)
- `F-REQ-14` — экспорт результата.
