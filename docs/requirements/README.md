# Требования

В этом каталоге описаны цели, пользовательские потребности, требования и ограничения локального переводчика технической литературы.

Требования определяют ожидаемое поведение системы и способы его проверки.
Наличие требования в документации не означает, что оно уже реализовано.

## Порядок чтения

Для знакомства с проектом:

1. Бизнес-требования: зачем создаётся система и что входит в MVP.
2. Пользовательские требования: какие задачи она должна решать.
3. Функциональные требования: как система должна вести себя.
4. Нефункциональные требования и технические ограничения.
5. Технические истории — при подготовке реализации.

При работе над конкретной функцией следует начинать со связанных требований, указанных в её карточке, а не перечитывать весь каталог.

## Идентификаторы

Каждое требование и каждая история имеют уникальный стабильный ID.

| Префикс | Вид записи | Пример |
|---|---|---|
| BR | Бизнес-требование | BR-001 |
| UR | Пользовательское требование | UR-01 |
| FR | Функциональное требование | FR-001 |
| NFR | Нефункциональное требование | NFR-001 |
| CON | Техническое ограничение | CON-001 |
| TS | Техническая история | TS-001 |
| REQ-TOKEN | Требования к токенизации | REQ-TOKEN-01 |

Правила:

- Нумерация ведётся независимо внутри каждого префикса.
- ID не зависит от положения записи в файле.
- При переносе записи между файлами её ID сохраняется.
- ID отменённых записей не используются повторно.
- В ссылках указываются ID и, по возможности, ссылка на соответствующий раздел.

## Статусы и принадлежность к MVP

Статус отражает согласование записи, а не готовность реализации.

| Статус | Значение |
|---|---|
| `draft` | Запись обсуждается и ещё не принята |
| `accepted` | Запись согласована владельцем проекта |
| `deferred` | Рассмотрение или выполнение отложено |
| `retired` | Запись больше не действует |

Для каждой записи отдельно указывается область поставки:

- `MVP` — входит в текущий минимальный продукт.
- `later` — рассматривается после MVP.
- `unassigned` — принадлежность ещё не определена.

В обязательства текущего MVP входят только записи со статусом `accepted` и областью поставки `MVP`.

Состояние реализации ведётся в [списке работ](../backlog.md), а результаты проверки — в карточках соответствующих функций.

## Связи между требованиями и реализацией

Основная цепочка:

Бизнес-цель → пользовательская потребность → требования к системе → проектное решение → задача → проверка.

Связи не обязательно образуют строгое дерево:

- одно функциональное требование может поддерживать несколько пользовательских требований;
- нефункциональное требование или ограничение может относиться сразу к нескольким функциям;
- техническая история может обеспечивать выполнение нескольких требований.

В записи указываются:

- основание: исходная потребность, требование или согласованное решение;
- связанные требования, если они есть;
- способ проверки и критерии приёмки;
- ссылка на карточку функции или технической работы, когда она появится.

Не нужно создавать фиктивные связи ради заполнения полей.
Если требование выведено из технической необходимости, следует явно указать её и обосновать.

## Минимальное содержание записи

Каждая запись содержит:

- ID и название;
- статус;
- область поставки;
- формулировку;
- основание;
- способ проверки и критерии приёмки;
- связанные материалы — при наличии.

Формат описания зависит от вида записи:

- для бизнес-требования — цель и критерий её достижения;
- для пользовательского требования — задача и ожидаемый результат;
- для функционального требования — условия, поведение и результат;
- для нефункционального требования — измеримая характеристика и условия измерения;
- для ограничения — обязательное условие и способ проверки соблюдения;
- для технической истории — результат работы и критерии его приёмки.

## Изменение требований

1. Добавить или изменить запись в соответствующем документе.
2. Проверить, не дублирует ли она существующие требования.
3. Указать основание, область поставки и критерии проверки.
4. Проверить влияние на связанные требования, проектирование и тесты.
5. Согласовать изменение до реализации изменяемого поведения.
6. Обновить связанные материалы в рамках того же изменения, либо явно зафиксировать необходимые последующие работы.

Новые записи создаются со статусом `draft`.
Согласование выполняет владелец проекта.

Редакционные исправления без изменения смысла не требуют повторного согласования требования.

История изменений хранится в Git.
Отдельный журнал всех правок в этом каталоге не ведётся.
