## Пользовательские сценарии
ПТ-01. Пользователь должен иметь возможность загружать документ через веб-интерфейс

ПТ-02. При невозможности загрузить документ пользователю должна возвращаться удобочитаемая информация о причине отсутствия возможности загрузки
```txt
К таковым относятся:
  - превышение размера документа
  - не поддерживаемый формат документа
```

ПТ-03. Допустимый размер загружаемого документа ограничен `200 Mb`.

ПТ-04. Пользователь должен видеть прогресс выполнения обработки документа

ПТ-05. Пользователю возвращается сообщение при ошибке выполнения этапов перевода документа
> Ошибка должна описывать конкретное поведение на каждом конкретном этапе перевода.
> Язык ошибки -- русский. 
> Отладочная информация содержится.

ПТ-06. Пользователь перед переводом выбирает из выпадающего списка предметную область/тематику перевода
> На момент запуска MVP достаточно одной тематики -- технической
> Перед переводом должна выполняться классификация тематики текста для выбора оптимальной модели или подхода

ПТ-07. Пользователь может запрашивать превью перевода
> опционально
> в рамках MVP не на первом месте

ФТ-02. Для распознавания доступен документ в форматах `pdf`

ФТ-03. Для распознавания доступен документ в текстовом формате
```txt
К текстовым форматам относятся `txt`, `md`, `ascii`
```

ФТ-04. Перевод осуществляется с помощью LLM

ФТ-05. Приложение ориентировано на перевод технической документации на русский язык
```txt
Предположительно в большинстве случаев язык оригинала документа  -- английский.
```

ФТ-06. Изображения в переводимых документах должны извлекаться и вставляться в перевод без изменений

ФТ-07. Перед выполнением перевода должен формироваться глоссарий документа
```txt
Глоссарий содержит термины и определения непосредственно из переводимого документа, а также термины, которые могут встерчаться в документе, но иметь двузначный перевод.
```
Глоссарий -- детерминированное хранилище `термин` -> `утверждённый перевод` с метаданными (источник-раздел, дата, статус). Хранить в `JSON`, не в векторном хранилище.

Глоссарий ≠ термины из текста документа

ФТ-08.  После формирования глоссария пользователь в него может вносить изменения
> Изменения могут вноситься до момента начала перевода всего текста документа.
> По окончанию внесения изменений активируется кнопка запуска перевода. 
> До окончания внесения изменений в глоссарий кнопка запуска перевода неактивна. Если пользователь не вносит изменений в глоссарий, он должен всё равно подтвердить своё решение нажатием кнопки "`Принять глоссарий`".

ФТ-09. Опционально возможна постобработка для вычитки и улучшения стиля лёгкой моделью

ФТ-10. В ходе перевода должна выполняться чистка файла от "мусорных" данных
> footer
> header

ФТ-11. Должен осуществляться запуск вызываемых моделей и приостановка простаиваемых
> Для эффективного расходования ресурсов
> `RoT` -- "поднять по запросу, выгрузить старый"

ФТ-12. Для локального инференса должны использоваться доступные модели

  - `translategemma-12b-it-8bit` -- технический перевод (регламенты, стандарты, 3gpp, RFC)
  - `translategemma-4b-it-4bit` -- предпросмотр страницы до похода в тяжёлую модель

ФТ-13. Извлечение структуры из pdf до перевода
> Выбор способа извлечения текста в зависимости от `OCR`/`Layout`

ФТ-14. Переведённый документ должен быть выгружен в читаемый формат:

К таковым относятся:
  - LaTeX
  - Markdown
  - pdf

> Выгрузка в pdf может осуществляться из md и LaTeX стандартными утилитами

ФТ-15. Спецсодержимое должно помечаться Docling-тегами
> Помечать как `no_translate`
> Как вариант -- оборачивать в protect-токены

Спецсодержимое:
  - таблицы, 
  - формулы, 
  - ASN.1
  - диаграммы 

ФТ-16. Приложение должно извлекать изображения "**как есть**" и возвращать их в переведённый документ
> См. ФТ-15
> Изображение = ресурс + плейсхолдер
> Схема работы с изображениями -- разработать по шагам!!! Вот ориентировочный план:
  - парсинг
  - защита от перевода - пометка тегом `no_translate`
  - хранение связи в State LangGraph
  - сборка в md/LaTeX/pdf
> рендер вместо извлечения

ФТ-17. Сформировать и вести в контроле версий глоссарий тематики
В рамках MVP возможно преждевременно. Далее перспективно. Использовать такой глоссарий в качестве образца.

## Ограничения и нефункциональные требования

НФТ-01. Допускается возможность запуска моделей либо локально, либо по API

НФТ-02. Для оркестрации процесса распознавания используется LangGraph

НФТ-03. Для работы приложения должны использоваться только библиотеки и пакеты с открытыми исходными текстами

НФТ-04. Запуск приложения должен осуществляться с одного ноутбука

НФТ-05. LLM, используемые локально, должны обладать подходящими лицензиями для работы без ограничений и с открытыми весами

НФТ-06. Допустимо ожидание при переключении модели (не миллисекунды, а секунды)
> с точки зрения пользователя функциональные кнопки не должны быть активными в момент переключения
> при простое более двух секунд должна появляться надпись "идёт переключение моделей"
> после надпись меняется на "модель готова" (см. ТИ-05)

## Технические истории

ТИ-01. Глоссарий хранится в формате `JSON`(`JSONL`)
> Формат  `JSON`(`JSONL`) с жёсткой схемой для хранения локальной версии переводчика (в рамках MVP, до развития в облачный продукт)
> Глоссарий формируется один раз на документ.
> По окончанию формирования глоссария модель освобождает память под транслятор.

ТИ-02. Когда используется модель `TranslateGemma`, то применяется строгий шаблон промпта
> При отклонении от шаблона качество падает, т.к. модель переходит в режим диалога.
> Шаблон: "Translate this from {src} to {tgt}: ..."

ТИ-03. Когда выполняется чанкование текста из pdf, размер одного чанка не должен превышать 2000 символов.
> Для ряда моделей типа `TranslateGemma` это техническое ограничение.
> Для остальных моделей может быть потерян контекст при большом размере чанка.
> Реально размер может быть ниже, порядка 500-1500.
> Возможно добавить ТИ для добавления в `verify` этапа проверки "количество предложений вход ≈ выход

ТИ-04. Когда тематика выбрана в `dropdown`, модель должна подниматься в фоне
> параллельно с `ingest`
> до нажатия кнопки начала перевода

ТИ-05. Когда пользователь выбрал тематику перевода, отображается надпись "модель готова"
> UX-честность
> пользователь видит, почему первые секунды ничего не происходит
> при выборе тематики меняется значение в конфигурационном файле `themes.yaml`
> код при этом не задействован
> повторный выбор той же тематики не вызывает повторно загрузку - идемпотентность
